# Gotchas learned the hard way

Cross-cutting across `daemon/`, `runner/`, `librarian/`, and `docker/` — kept
here rather than split across each crate's `AGENTS.md`, since several of
these bugs only make sense read together (e.g. the runner-reattach mitigation
and the daemon-side tmux/psmux crash it works around).

- **`RALPHUS_BIND_ADDR` is a deliberately narrow escape hatch, not a general "listen on the network" flag.** Both `ralphus-daemon` and `ralphus-librarian` bind `127.0.0.1` unless this env var is set (RAL-225); only `docker/docker-compose.yml` sets it (to `0.0.0.0`, since a container's loopback isn't reachable through Docker's published-port mapping). Setting it to `0.0.0.0` outside a container exposes the daemon's unauthenticated HTTP API to your whole LAN — don't set it in a bare-subprocess setup.
- **Cell `cwd` must be a real path for the OS the daemon runs on.** On Windows, an MSYS/Git-Bash `/tmp/...` path will not resolve in native-Windows Python — use a Windows path. `cwd` is mandatory and validated.
- **Runner command**: the daemon spawns `RALPHUS_RUNNER_CMD` (default `ralphus-runner`). In dev, `scripts/build-debug.sh`/`.cmd` build it with `cargo` and point `RALPHUS_RUNNER_CMD` at the fresh `target/debug/ralphus-runner` exe — a normal incremental Rust rebuild, no venv, no editable install. `dist/ralphus-runner.exe` (built by `scripts/build-release.cmd`) is a standalone release exe; only rebuild it when something changed since the last one.
- **The full review flow has a live-Ollama integration test** — `daemon/tests/reviews_derive.rs::full_flow_validate_submit_run_and_ollama_resolves_conflict`. It **skips** unless Ollama is up on `127.0.0.1:11434`, the resolver model (`RALPHUS_RESOLVER_MODEL`, default `qwen3:8b`) is pulled, and a `ralphus-runner` is found.
- **Monorepo integration test** — `daemon/tests/monorepo.rs` has three always-run pipeline tests and one live-Ollama test, `#[ignore]`d by default. Run the live test with `cargo nextest run -p ralphus-daemon --test monorepo full_monorepo_flow -- --ignored --nocapture`.
- **Model selection** is per-cell in TOML: `agent = "ollama"` + `model = "qwen3:8b"` for local; `agent = "claude"` (default) uses Anthropic (needs `ANTHROPIC_API_KEY`).
- **`prompt`-kind proof steps** run for real, reusing the owning cell's resolved backend through the same `Runner`/`ralphus-runner` path. The runner wraps the proof prompt and parses the final `RALPHUS_PROOF: PASS`/`FAIL` line. Small local models don't put the marker alone on its own line — parsing searches the whole output and trusts the last occurrence. No verdict found = FAIL (fail closed).
- **Port clash**: the old claudectl also uses 7474/7890; the daemon port is not yet CLI-configurable, so don't run both.
- **Submitting goes to `Pending` (schedulable now)**, not `Queued`. `hold=true` stages as `Queued`; `/activate` promotes it. (The predecessor's silently-`Queued`-forever bug — FINDINGS §2.4.)
- **`keygen` is never shipped.** It is not in the release build scripts and should not be added. It is a workspace member only so `cargo build --all` can catch compile errors in CI.
- **A tmux-wrapped cell's pane can vanish mid-run with no clean explanation** on the Windows tmux-alternative this project targets (`psmux`) — see the gitignored `PSMUX_CRASH_NOTES.local.md` if present for background. `SubprocessRunner::run_via_tmux` (`daemon/src/runner.rs`) mitigates this: once a `claude-code`/`codex` cell's `agent_session_id` has been captured live (from the `stream-json` init event or Codex's `thread.started` event, forwarded over the `RALPHUS_EVENT:` marker), a pane that goes unreachable for `MISSING_SESSION_STRIKE_LIMIT` consecutive polls triggers a bounded auto-reattach (`claude -p --resume <id>` or `codex exec resume <id>`, up to `SubprocessRunner::MAX_REATTACH_ATTEMPTS` times) in a fresh tmux session under the *same* deterministic name — so the board's "Show Live View"/"Open Terminal Log" buttons transparently start working again with no UI-side change. The overall `timeout_sec` budget is shared across every attempt, never reset by a reattach. Every stage (tmux session lost / reattach attempt / giving up) is logged via both `rlog!` and a `tmux-reattach`-scoped Cartographer note carrying attempt/elapsed/reason/last-error, so a real occurrence is fully diagnosable from Cartographer alone (see [[logging-policy]]). Only exercised for `agent = "claude-code"`/`"claude-cli"`/`"codex"`/`"codex-cli"`; other agents still fail outright on a lost pane, exactly as before.
- **A running dev daemon/librarian locks its own exe, so `--all-targets` can't build.** On Windows, `cargo build`/`cargo test` with `--tests` or `--all-targets` for `ralphus-daemon` or `ralphus-librarian` includes the `[[bin]]` target and tries to relink `target/debug/ralphus-daemon.exe`. If the dev stack is running from that path the file is locked and the build dies with ``failed to remove file `...\target\debug\ralphus-daemon.exe` / Access is denied. (os error 5)`` — or, especially when ralphus itself is the one driving the work (a ralphus cell/proof step dogfooding on the ralphus repo, so its own dev daemon holds the lock), the build/link step can sit there and hang instead of failing cleanly. This is environmental, not caused by your change. Use `cargo nextest run -p ralphus-daemon --lib` (and the same for `ralphus-librarian`) — `--lib` never touches the bin target and still runs every unit test in `daemon/src/*.rs`. Other workspace members are unaffected and can use `--all-targets` normally. Integration tests under `daemon/tests/` *do* need the bin relinked, so they cannot run at all while the dev stack is up — say so explicitly rather than implying full coverage, and don't stop the daemon to get around it ([`agent-conduct.md`](agent-conduct.md)).
- **Don't add `--all-features` to clippy.** `cargo clippy -p ralphus-daemon --all-features` fails to compile with `couldn't read daemon/src/../assets/tmux/windows/tmux.exe` — an `include_bytes!` in `daemon/src/tmux.rs` behind a bundled-tmux feature whose binary asset isn't in the checkout. Pre-existing and unrelated to whatever you changed. Use the documented command as written: `cargo clippy --all-targets -- -D warnings`.
- **Throwaway worktrees need a SHORT path on Windows, or removal eats main-repo files.** `git worktree add` under a deep scratchpad path (`C:\Users\KORINK~1\AppData\Local\Temp\claude\...\scratchpad\...`, already ~110 chars before this repo's own `.git/.ralphus/w/...` and `target/debug/deps/...` nesting) blows past MAX_PATH during `git worktree remove --force`: it fails with `failed to delete '...': Filename too long` **and leaves the delete half-done, having removed files from the main repo working tree** (observed with `Cargo.toml`; recovered with `git checkout --` only because it was unmodified and tracked). Use a short path such as `/c/Users/korinkite/rw191`, and after any worktree removal check `git status --short | grep -E "^ ?D"` for collateral damage.
- **Docker bind mounts must be driven from PowerShell, not Bash, on Windows.** Passing a Unix-style source path to `docker run -v` / `docker compose` from Git-Bash/MSYS either errors (`invalid mount path: 'C' mount path must be absolute` — MSYS mangles the colon) or, with `MSYS_NO_PATHCONV=1`, silently mounts an empty path inside Docker Desktop's own Linux VM instead of the intended host directory. The container comes up healthy and the mount is just wrong, which is far sneakier than an error — it's how `docker/docker-compose.yml`'s workspace mount (RAL-225) appeared broken. Use the PowerShell tool with a real Windows path (`$env:TEMP\...`) as the mount source. Bash is fine for `docker build`/`ps`/`logs`/`exec` — anything not passing a host path as a mount source.
- **Guardian's stacked rebase leaves verbatim duplicated blocks.** `daemon/src/guardian_merge.rs` replays commits repeatedly, and conflict resolutions on the stack keep emitting the same `let` binding, `#[test]` fn, doc-comment paragraph, or Markdown section twice in a row (seen in `daemon/src/pr.rs`, `scheduler.rs`, `server.rs`, `librarian/src/lib.rs`, `docs/glossary.md`). A duplicated `let` shadows rather than errors, surfacing only as a clippy `unused_variables`/`unused_mut` that's tempting to "fix" with an underscore while keeping dead logic. So: **never silence an `unused_mut`/`unused_variables` here without first checking for a duplicated block above it**, and on a conflict or final-proof pass scan for adjacent identical blocks before trusting clippy:
  ```bash
  # duplicate test fn names within a file
  for f in $(git ls-files '*.rs'); do grep -A1 '#\[test\]' "$f" \
    | grep -oE 'fn [a-zA-Z0-9_]+' | sort | uniq -d | sed "s|^|$f: |"; done
  ```
  plus a comparison of `lines[i:i+L]` against `lines[i+L:i+2L]` for L in 4..60 over `git ls-files '*.rs' '*.html' '*.md'`.
- **A proof pass inherits red tests from earlier in the stack — fix them anyway.** When a proof pass hits a failing test in a file the branch barely touched, "pre-existing, therefore not mine" is the wrong stopping point: the bar is that the suite passes in *this* worktree. Diff the function against its siblings and its own doc comment — the intended behavior is usually written down right there. (`forge::tests::unstack_is_a_no_op_for_gitlab` failed because `ForgeClient::unstack` in `daemon/src/forge.rs` lacked the early-return guard its doc comment promised and both sibling methods had; a one-liner.)
- **`ralphus-daemon`'s unit tests are not hermetic against your shell's `RALPHUS_CONFIGURATION_PATH`/`RALPHUS_CONFIG_HOME`.** `daemon/src/server.rs`'s route handlers (`current_user`, `require_current_user`, and every direct `crate::config::load_daemon_config()` call site) read the *real* env/filesystem with no test-time override, unlike `agent_profiles.rs`/`machine_targets.rs`'s own `_with(...)` testable variants. If your shell has `RALPHUS_CONFIGURATION_PATH` (or the global `~/.config/ralphus/config.toml`) pointing at a file that sets `[daemon].default_user`, dozens of `server::tests::*` that hit a route without `?user=...` will fail with `400 unknown_user` instead of their expected status — the test's in-memory store never registered that name. Not a flake and not caused by whatever you're editing: confirmed by rerunning the same suite with `RALPHUS_CONFIGURATION_PATH` unset (all pass) vs. set to a `default_user`-bearing file (~50 failures, always the same tests). CI is unaffected (no such env var there). **Unset `RALPHUS_CONFIGURATION_PATH` before running `cargo nextest run -p ralphus-daemon`** if your shell normally carries one for daemon dev work, e.g. `env -u RALPHUS_CONFIGURATION_PATH cargo nextest run -p ralphus-daemon --lib`.
- **A stacked-rebase conflict resolution can silently reintroduce a fixed bug into synchronization-primitive code, and that shows up as an infinite hang, not a `FAILED` test.** Rebasing `RAL-281` onto `RAL-280` in a guardian merge produced a conflict in `daemon/src/scheduler.rs`'s `Semaphore::new`; the agent resolution kept the pre-`RAL-280` initializer (`permits: permits.max(1)`) instead of the corrected one (`permits: capacity`), so `permits == 0` ("unlimited") still left the live counter starting at `1`. The unit test `scheduler::tests::semaphore_zero_means_unlimited` acquires more than one permit and then blocks forever on `Condvar::wait` with nothing left to wake it. Because `cargo test` runs every unit test in one process, that single hang froze the *entire* `--all-targets`/`--lib` run — no `FAILED` line, no `test result:` summary, just silence — which repeatedly tripped the mailbox's 300s-stall escalation instead of ever failing outright, and looked identical to "the suite is just slow" until someone diffed completed test names against `cargo test -- --list` to find the one that never printed `ok`.
  - **Authoring rule**: a test that exercises a real blocking wait on a semaphore/mutex/condvar/channel must never be able to block indefinitely on a regression. Bound it — run the blocking call on a thread and join with an explicit timeout, or assert with a non-blocking `try_acquire`-style call — so a real bug fails fast and loud instead of freezing the whole binary.
  - **Diagnosis rule**: if a `cargo-test` proof step or CI job stalls past its normal runtime with no failing-test output, don't assume it's merely slow. Bisect for a non-terminating test first, and specifically re-diff any synchronization-primitive constructor near a stacked branch's conflict-resolved hunk — resolution can revert an already-fixed initializer without leaving a visible duplicate block (contrast with the entry above).
- **"The daemon dies / the board is unconnectable after ~2 minutes" was a socket-exhaustion cascade, not a daemon bug — the root cause is connection-per-request proxying.** The chain, root cause first:
  - **Root cause: the librarian proxied every `/api/*` board poll to the daemon with ureq's free `get`/`post`/`delete` functions, which build a throwaway `Agent` per call → a fresh TCP connection to the daemon per request, dropped the instant the body is read.** On Windows every closed socket sits in `TIME_WAIT` ~120s holding an ephemeral port; the board polls a dozen endpoints every ~2s per open tab, so the ~16k-port dynamic range (49152–65535) drains within a couple of minutes of heavy use — matching the "~2 min" and "TIME_WAIT count in the thousands" symptoms. **Fix: `librarian/src/server.rs`'s `daemon_client()` — one shared pooled HTTP client (`ureq::Agent`, with raised `max_idle_connections*` since ureq defaults to 1/host) that all proxying reuses via keep-alive**, so steady-state board traffic reuses ~a handful of connections instead of churning one per poll. Verified: 150 rapid polls add ~0 new `TIME_WAIT`. The SSE proxy (`/api/events`) deliberately stays on the un-pooled path — it's long-lived and must not inherit the pool's read timeout. **Any new librarian→daemon (or daemon→anywhere loopback) HTTP call must go through a pooled client, never a per-call ureq free function.** (Note the word trap: `ureq::Agent` is an HTTP client with a socket pool, unrelated to a ralphus *agent* — the AI backend that runs a cell; the helper is named `daemon_client`, not `*_agent`, to keep that distinct.)
  - **Amplifier: tiny_http 0.12's accept thread treats *any* `accept()` error as fatal** — it reports the error only via the `log` crate (no logger is installed in either binary, so the message vanishes) and exits, after which `incoming_requests()` just ends. Once ephemeral ports/handles ran out, one `accept()`/socket error therefore silently ended the whole librarian or daemon mid-flight. Both `daemon/src/server.rs` and `librarian/src/server.rs` now treat that as recoverable (log loudly, rebind the listener, keep serving) — a "listener stopped accepting connections; rebinding" line means this safety net fired and the machine was under socket/handle pressure. This is defense-in-depth, **not** the cure; if it ever fires repeatedly, find the connection-churn source, don't rely on the rebind.
  - **Disguise 1: `scripts/build-debug.cmd`/`.sh` kill the daemon the moment the librarian foreground process exits**, so a librarian death always *looked like* a daemon death. Both scripts now announce this teardown (and the `.cmd` keeps the hidden daemon's stderr in `logs/daemon-stderr.log`) instead of doing it silently.
  - **Disguise 2: the daemon's kill-on-close job object (`daemon/src/jobobject.rs`)** means any daemon exit instantly terminates every running cell/agent with no final log flush — so the wreckage never points back at the trigger.
  - **Diagnosis trap: a user-level `RALPHUS_CONFIGURATION_PATH` config can move `[daemon].log_path`**, so "the daemon log went quiet" may just mean the log moved — find the live file before concluding logging (or the daemon) is broken.
- **`build-debug.cmd`: never add `-RedirectStandardError`/`-RedirectStandardOutput` to the daemon's `Start-Process` launch line.** The script captures the daemon's PID with `for /f ... in ('powershell ... (Start-Process ... -PassThru -WindowStyle Hidden).Id')`. Adding a file redirect makes PowerShell hold the redirect pipe open for the *entire lifetime* of the (long-running) daemon, so the `for /f` reading that command's output never sees the pipe close and the line **hangs forever** — the script never reaches the foreground `ralphus-librarian.exe serve` line, so the board (7474) never comes up while a daemon nonetheless survives on 7890. This looked exactly like "the librarian silently fails to start." The daemon already writes everything to its configured `log_path`, so capturing stderr here is redundant anyway. (Verified empirically: identical `for /f` line returns the PID in ~1s without the redirect, hangs indefinitely with it.)
- **A `git`-reported worktree path and a `Path::canonicalize()`-derived one are different strings for the identical directory on Windows, and any code that compares them as raw strings will silently never match.** `git rev-parse --path-format=absolute --git-common-dir` (used by `daemon/src/reviews.rs`'s `worktree_project`) prints forward-slash paths even on Windows; `Path::canonicalize()` (used by `ralphus project git`'s registration path, `cli/src/commands/project.rs`) returns backslash-separated ones. This was the root cause of RAL-318's Triage auto-review pooling never matching a threshold set against the same project by name (bugs 1 and 3): the pool key computed at submit time and the key a threshold was set under were never byte-identical, so a "matching" pool/threshold pair silently became two unrelated ones. Fixed by routing every pool-key-producing/consuming site through one normalizer (`daemon/src/triage.rs`'s `pool_key_for_path`/`resolve_pool_key_input`: canonicalize, strip the `\\?\` verbatim prefix, force forward slashes) instead of comparing raw path strings directly. **Any new code that keys persisted state off a filesystem path derived from two different sources (a shelled-out git command vs. a Rust `std::fs` call, or similar) must normalize both sides through a shared function before comparing or using one as a lookup key** — never assume they already agree.
